# MindLink 产品规格与任务拆分

本文按 MindLink 的**最终形态**写：产品完成时应当是什么样子、用什么架构组织、拆成哪些 issue。不分版本，也不先做简化版再迭代；每个 issue 都按最终的要求实现，验收通过才算完成。每个 issue 的完整需求和验收标准写在 issue 正文里，本文只写整体结构。

这是 MindLink 唯一有效的规划文档。原来的 [2026-10 开发计划](https://github.com/SAIR-club/Episteme/blob/archive/docs-2026-10-19/docs/planning/development-plan-2026-10.md)（已归档）中仍然有效的方向和关键设计决定，以最新版本收录在第 1 节。

现状：Episteme `main` = `3d335be`，平台一侧的身份、可见性、发布、线程、场景记录、托管确认和分层 recall 都已合并；MindLink `main` = `7f2d79a`，只完成了改名和固定 Episteme 版本，其余从零开始。

## 1. 最终形态

> 一个学习者在自己的 Claude Code / Codex / WorkBuddy 里学一门课：MindLink 按他组装的工作流安排学习环节，在引导环节预测他接下来想问什么，把他确认过的理解跨会话、跨 agent 记住；他可以把理解发布给同课同学，也能看到同学普遍卡在哪里。

完成时同时满足：

1. **能部署**：一台 Linux 服务器上一条命令起一个共享服务，多名同学各用自己的令牌；本地单人模式同样可用。
2. **能接入**：Claude Code、Codex、WorkBuddy 安装 skill 包或按说明配置后，都会在正确的时机自动调用工具。
3. **三个创新点完整**：共享（发布、浏览、复用、更新、同课卡点）；自组装工作流（分级积木、内置工作流和片段、用户自写和课程内分享）；引导式提问（作为积木，三档强度，每次给出若干预测问题，统计点选率）。
4. **前端完整**：项目、审阅与托管、理解查询与历史、线程树、积木库与工作流组装器、共享、项目首页，全部可用。
5. **经过真人验证**：试点同学用真实的学习会话跑过，数据如实记录。

本轮做第 3、4 条，以及第 1 条中的本地模式和 `--shared` 模式本身。服务器部署、宿主接入和真人验证放到最后（第 7 节）。

产品范围之外：自研或训练模型；多 agent 并行；论坛、评论、点赞、排行；跨课程的公开积木市场。

### 1.1 方向

- **三层结构。** Episteme 是平台；上面是 MindLink（学习）和 Discussion（`SAIR-club/discussion`，目前只留接口）。
- **定位**（依据[竞品调研](competitive-analysis.md)）：三个创新点单拿出来都有人做过，真正的差异在它们的交叉处：一个跨 agent、由人确认的理解记录，加上同一门课里大家普遍卡住的点，用来驱动引导式提问。共享是引导的燃料，不是一个独立功能。一句话：**一个记得你理解到哪、也记得别人卡在哪的学习层。**
- **确认权永远在用户手里。** 默认由学习者确认理解；也可以把确认托管给 AI，并且随时收回。
- **所有 agent 共享一份全局记忆。** Claude Code、Codex、WorkBuddy 等宿主 agent 都通过 MCP 连接同一个服务，每个人用自己的令牌。
- **试点：** 一门课 × 一届同学。共享在架构上面向全网，但种子数据、演示和测试都围绕这一门课。

### 1.2 关键设计决定

| #   | 决定 | 落在哪里 |
| --- | ---- | -------- |
| D1  | Episteme 是平台，MindLink 是应用；每个能力只有一个归属，两个仓库只通过固定的接口协作，MindLink 用 `episteme.ref` 固定所依赖的 Episteme 版本 | ADR 0013 |
| D2  | 部署成一个共享服务，每个用户用自己的令牌登录，每个人的所有 agent 也用自己的令牌连接 MCP，这就是"全局记忆"；仍保留本地单人模式 | ADR 0012 |
| D3  | 共享是一条**发布记录**，不是复制。复用会在复用者自己的状态里写一条事件，并注明来源于哪条发布。可见性只由 Core 里的一个函数判断 | ADR 0014 |
| D4  | 对话线程归 Episteme。原始对话作为 source 存档，从不进入图谱，也从不共享；总结后的对话可以发布；多线对话就是线程的分叉 | ADR 0015 |
| D5  | 托管确认：用户可以按项目授权服务代为确认 agent 的提议，每条都标记为 `delegated`，可以撤回；发布、复用、冲突永远由本人操作 | ADR 0016 |
| D6  | 进度只是界面上的显示：从多维状态算出一个 0–1 的值，从不保存，也从不回写。Core 里仍然没有单一分数 | MindLink 应用层 |
| D7  | 学习环节是**分级的积木**：基础积木 → 活动积木 → 工作流，每一级只能引用更低一级；积木只有声明式的内容，没有代码，所以可以安全分享；引擎不认识任何具体的积木 | MindLink（第 2.5 节） |
| D8  | 引导式提问和复习都是活动积木（`guide`、`review`），可以放在工作流的任意位置、放任意次。强度有三档：直接讲（tell）、给提示（hint）、只提问（ask），所有积木共用。引导的依据是学习者自己的状态和同课卡点；指标是预测问题的点选率，以及从开始学到通过自测的时间 | MindLink（第 2.5 节） |
| D9  | Episteme 和 MindLink 都不自带模型。对话总结、引导问题都由宿主 agent 的模型生成，MindLink 只提供素材、负责校验和记录 | ADR 0008、0011 |
| D10 | 学习项目只存设置，不存学习数据；图谱里的节点带上项目的 `scope:` 标签，`recall` 优先取当前项目，但可以跨项目关联 | MindLink（第 2.4 节） |

## 2. 架构

### 2.1 分层

| 层 | 包含 | 可以依赖 |
| -- | ---- | -------- |
| L3 组装 | `app.ts`、CLI、项目首页 | 所有下层 |
| L2 功能 | 理解（审阅与托管、理解查询与概览、线程树）、积木（格式、编排引擎、积木用到的工具、积木页面）、共享 | L1、L0 |
| L1 基础 | 学习项目、账户 | L0 |
| L0 平台访问层 | `@mindlink/platform`：全仓库唯一 import Episteme 的地方 | Episteme |

前端框架被所有页面共用，不属于某一层。积木的内容（`.md` 和 `.yaml` 文件）不是代码，由积木系统加载。

### 2.2 规则

由 `tests/architecture.test.ts` 根据一份层级表检查，违反就让 CI 失败：

1. 只能依赖下层；同一层的功能之间不互相 import。
2. 下层需要上层的数据时，由下层定义接口、上层实现、`app.ts` 注入。
3. 每个功能只通过自己的 `index.ts` 导出公开的函数和类型，不能 import 别的功能内部的文件。
4. 功能内部，逻辑（纯函数和用例）只依赖 L0 的接口；MCP 工具和 REST 路由只由 `app.ts` import。
5. 每个功能的页面只调用自己的 REST；需要拼接多个功能的页面（项目首页）放在 L3。
6. 只有 `@mindlink/platform` 可以 import `@episteme/application` 和 `@episteme/mcp`；积木引擎的源码里不出现任何内置积木的 id；前端代码里不出现 `innerHTML`、`outerHTML`、`insertAdjacentHTML`。

### 2.3 平台访问层

各功能都不直接碰 `SceneView`，只用 `@mindlink/platform` 的接口：读状态、提议与蒸馏、场景记录（带 schema 版本）、读线程、浏览发布、时钟。每个接口都有内存实现（`@mindlink/platform/testing`），各功能可以脱离服务单独测试，也不必等 Episteme 补完缺口才开工。

### 2.4 学习项目

学习项目是**某门课上的一个学习空间，只存设置，不存学习数据**：名字、所属课程（决定 `scope:` 标签）、用哪个工作流、默认引导强度、是否开启托管。目标、截止时间、已有基础由 `goal`、`diagnose` 积木在对话中问出来，写回项目设置。进度、画像、待复习的条目都是别的功能按项目范围读出来的。课程是同学们共用的范围；项目是个人的，一个项目最多属于一门课。

### 2.5 积木系统

| 级 | 是什么 | 可以引用 | 例子 |
| -- | ------ | -------- | ---- |
| 基础积木 | 一个最小的教学动作，可以被很多活动复用 | 积木用到的工具 | 预测问题、挑出待复习、自测、复述检查、提交蒸馏 |
| 活动积木 | 一个完整的学习环节 | 基础积木、工具 | `guide`、`review`、`feynman`、`explain` |
| 工作流 | 一次学习的安排 | 活动积木、片段 | `speedrun`、`practice`、`deep` |

- **目录结构类似 skill**：`BLOCK.md`（元数据和主说明，含 tell / hint / ask 三档）、`references/`（按需读取的资料）、`examples/`（示例对话，同时作为测试数据）。
- **按需加载**：引擎按活动排进度；`workflow_next` 只返回当前活动当前强度的说明和子步骤清单；agent 执行到某个基础积木时再用 `block_read` 读详细说明。
- **引擎不认识具体积木**：所有行为都来自积木自己的声明。积木声明自己的结果有哪些字段，`workflow_report` 按声明记录，统计由引擎通用地算，点选率就是 `guide` 的结果统计。
- **积木用到的工具**归积木模块，只做通用的读取：状态缺口、最近对话、同课卡点、待复习条目。启动时校验每块积木引用的工具都存在。
- **三个来源**：内置、课程、用户；同名不覆盖。

内置的活动积木，以及各自主要推动的状态维度（一块积木有没有起作用，可以在图谱上直接看出来）：

| 阶段 | 积木 | 做什么 | 推动的维度 |
| ---- | ---- | ------ | ---------- |
| 定向 | `goal` 目标设定 | 速通、应用还是长期积累；截止时间；写回项目设置 | — |
|      | `diagnose` 基础诊断 | 已经会什么、缺哪些前置知识；写回项目设置 | 读取全部维度 |
|      | `map` 领域地图 | 先搭出骨架：这个领域分成哪几块 | exposure |
|      | `path` 路径规划 | 按目标和基础排出学习顺序 | — |
| 获取 | `sources` 资料检索 | 公开资料，加上同课的相关发布 | source |
|      | `explain` 概念讲解 | 按学习者的基础定制讲解深度 | exposure |
|      | `example` 例子与类比 | 具体例子、跨领域类比 | exposure、transfer |
| 构建 | `model` 建模与推导 | 理工科的公式、推导、建模 | evidence |
|      | `practice` 练习应用 | 做题、写代码、做案例 | evidence、confidence |
| 检验 | `recall` 自测提取 | 主动回忆，不看材料作答 | confidence |
|      | `feynman` 费曼复述 | 用自己的话讲一遍，AI 找出漏洞 | articulation |
|      | `conflict` 误解与冲突 | 识别矛盾，保留冲突，不替学习者裁决 | conflict |
|      | `transfer` 迁移关联 | 连到别的学科或已经学过的内容 | transfer |
|      | `guide` 引导提问 | 根据状态缺口、最近对话和同课卡点预测接下来想问的问题，以选项展示 | articulation |
| 沉淀 | `distill` 总结蒸馏 | 总结对话，生成候选理解，交给学习者确认或托管 | 写入图谱 |
|      | `compare` 共享对照 | 和别人发布的理解对照，发现不同的路径或分歧 | conflict、source |
|      | `review` 间隔复习 | 按 confidence 和距上次接触的时间安排回顾 | confidence |
- 格式的具体写法之后再细化（第 8 个 issue）。

## 6. 分支与 PR 规则

- 一个子 issue 一条分支，从最新的 `origin/main` 切出，命名为 `<type>/<short-topic>`，PR 正文写 `Closes SAIR-club/MindLink#<编号>`。总 issue 不直接对应 PR。
- 不直接推 `main`，不在未合并的分支上叠分支，不用 `--no-verify`。Windows 上用 `git clone -c core.autocrlf=false`。
- 一个 PR 只做一个子 issue；做到一半发现范围太大，就再拆一个子 issue。
- 改平台访问层的接口、层级表或积木格式，先在对应的总 issue 下讨论并取得同意，再单独开一个 PR。
- 代码、注释、commit 用英文；界面文字和积木内容用简体中文。不新增依赖（确实需要时先在 issue 下说明理由）。`pnpm check` 必须全绿。
- 遇到与 issue 冲突或拿不准的地方，停下来在 issue 下提问，不要猜着实现。
