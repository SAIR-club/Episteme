# 开发计划：2026-10-19 至 2026-11-15

本文是一个月冲刺的总计划：要做什么、为什么这样划分、谁依赖谁、按什么顺序做。每一项工作都对应一个 GitHub issue，issue 里有可以直接交给 AI 编码助手的提示词。本文只在方向或拆分改变时修改，进度看 issue 和 PR。

## 1. 方向

2026-10-10 和 2026-10-17 两次讨论确定的方向：

- **三层结构。** Episteme 是 Core 平台；上面是 **MindLink**（原 `SAIR-club/learner`，改名中）和 **Discussion**（`SAIR-club/discussion`，本月只留接口）。
- **三个核心创新点：**
  1. **共享。** 理解可以共享到全网。共享的是 AI 总结过的对话（保留原始对话的节点结构）和理解层，不共享原始对话。复用别人的理解要本人同意，并记录出处。
  2. **工作流自定义。** 学习的每个环节是一个可插拔模块。有默认工作流，可以调整，用户也可以自己写模块。编排方式由用户选：交给 agent 决定，或者用固定步骤（省 token、省时间）。
  3. **引导式提问。** 苏格拉底式启发，问题从学习者的认知状态里生成，不预设题目。目标是"AI 比你都懂你想问什么"。
- **确认权永远在用户手里。** 默认由学习者确认理解；用户也可以把确认权全权托管给 AI，并且随时收回。
- **所有 agent 共享一份全局记忆。** 一个学习项目只有一份记忆，Claude Code、Codex、WorkBuddy 等宿主 agent 都通过 MCP 连接同一个 Episteme 服务。另有一个 web 入口，用来管理对话、理解程度和学习安排。
- **定位**（依据[竞品调研](competitive-analysis.md)）：三个创新点单拿出来，每一个都有人做过；真正的差异在它们的交叉处。一个跨 agent、由人确认的理解记录，加上同一门课里大家普遍卡住的点，用来驱动引导式提问。所以共享是引导的燃料，不是一个独立功能。一句话定位：**一个记得你理解到哪、也记得别人卡在哪的学习层。**
- **试点：** 一门课 × 一届同学（课程待定）。共享在架构上面向全网，但种子数据、演示和测试都围绕这一门课。
- **优先级：** 本月比赛优先，三个创新点全部做完。面向开发者的 Episteme 对外发布（英文 README、一行安装、演示视频）排在最后一周，进度落后时第一个顺延。
- **不做的：** 自研或训练模型、多 agent 并行、论坛功能、动态学科边界算法、判断新并入内容是"新理解"还是"有争议"的 agent（后续再做）。

## 2. 关键设计决定

下面每一条都会改变已有的约定，所以都落在一条 ADR 里。没有 ADR 的条目，只能在应用层实现。

| #   | 决定                                                                                                                                                                                                                       | 落在哪里                         |
| --- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------- |
| D1  | Episteme 是平台，MindLink 是应用；每个能力只有一个归属，两个仓库之间只通过固定的接口（contract）协作，MindLink 用 `episteme.ref` 固定所依赖的 Episteme 版本                                                                | ADR 0013（草稿已推送）           |
| D2  | **部署成一个共享服务。** 要共享到全网，就不能每人只跑一个本地服务。MVP 部署一个服务（先在校内服务器），每个用户用自己的令牌登录；仍保留本地单人模式。每个人的所有 agent 都用自己的令牌连接远程 MCP，这就是"全局记忆" | ADR 0012（#17，需要扩展到远程）  |
| D3  | 共享是一条**发布记录**，不是复制。复用会在复用者自己的状态里写一条事件，并注明来源于哪条发布。可见性只由 Core 里的一个函数判断                                                                                             | ADR 0014（草稿已推送）           |
| D4  | **对话线程归 Episteme。** Discussion 也需要线程，所以线程不放在 MindLink。原始对话作为 source 存档，从不进入图谱，也从不共享；总结后的对话可以发布；多线对话就是线程的分叉（fork）                                            | ADR 0015（新写）                 |
| D5  | **托管确认。** 用户可以按项目授权"AI 全权托管"：agent 提的建议由服务代用户确认，每条都标记为 `hosted`，并且可以撤回。即使在托管状态下，发布、复用、裁决冲突也必须由本人亲自操作                                              | ADR 0016（新写），修订 AGENTS.md |
| D6  | **掌握度滑块只是界面上的投影。** MindLink 的界面从多维状态算出一个 0–1 的值来显示，这个值从不保存，也从不回写。Core 里仍然没有单一的 mastery 分数                                                                          | MindLink 应用层，无需 ADR        |
| D7  | **模块是声明式文件**（Markdown 加 frontmatter），不含可执行代码，所以用户写的模块可以安全分享。模块由宿主 agent 执行：MindLink 通过 MCP 把"下一步做什么"告诉 agent                                                       | MindLink 应用层                  |
| D8  | **引导式提问是贯穿所有模块的一种模式，不是单独的模块。** 有三档强度：直接讲 / 给提示 / 只提问。每轮对话后，系统根据学习者的状态预测 3 个"你接下来想问的问题"；预测的依据除了这个人自己的状态，还有同一门课同学普遍卡住的点（来自共享的发布）。指标有两个：预测问题被用户直接点选的比例，以及从开始学到通过自测所用的时间                        | MindLink 应用层                  |
| D9  | Episteme 不自带模型。对话总结、引导问题都由宿主 agent 的模型生成，Episteme 负责校验和保存（延续 ADR 0011 的做法）                                                                                                          | 延续 ADR 0008/0011               |
| D10 | **学习项目**是 MindLink 的一条记录（包括目标、基础、工作流、画像），存在 Episteme 提供的"场景记录"里；图谱里的节点带上项目范围（scope）标签。`recall` 优先取当前项目的节点，但可以跨项目关联                               | ADR 0015 的一部分                |

## 3. 学习环节模块（MindLink 内置 16 个）

每个模块推动 Episteme 已有的几个状态维度，这样一个模块有没有起作用，可以在图谱上直接看出来。

| 阶段 | 模块 id      | 名称       | 做什么                                     | 推动的维度          |
| ---- | ------------ | ---------- | ------------------------------------------ | ------------------- |
| 定向 | `goal`       | 目标设定   | 速通、应用还是长期积累；截止时间           | —                   |
|      | `diagnose`   | 基础诊断   | 已经会什么、缺哪些前置知识                 | 读取全部维度        |
|      | `map`        | 领域地图   | 先搭出骨架：这个领域分成哪几块             | exposure            |
|      | `path`       | 路径规划   | 按目标和基础排出学习顺序                   | —                   |
| 获取 | `sources`    | 资料检索   | 公开资料，加上共享图谱里的相关发布         | source              |
|      | `explain`    | 概念讲解   | 按学习者的基础定制讲解深度                 | exposure            |
|      | `example`    | 例子与类比 | 具体例子、跨领域类比                       | exposure、transfer  |
| 构建 | `model`      | 建模与推导 | 理工科的公式、推导、建模                   | evidence            |
|      | `practice`   | 练习应用   | 做题、写代码、做案例                       | evidence、confidence |
| 检验 | `recall`     | 自测提取   | 主动回忆，不看材料作答                     | confidence          |
|      | `feynman`    | 费曼复述   | 用自己的话讲一遍，AI 找出漏洞              | articulation        |
|      | `conflict`   | 误解与冲突 | 识别矛盾，并且保留冲突，不替学习者裁决     | conflict            |
|      | `transfer`   | 迁移关联   | 连到别的学科或已经学过的内容               | transfer            |
| 沉淀 | `distill`    | 总结蒸馏   | 总结对话，生成候选理解，交给学习者确认或托管 | 写入图谱            |
|      | `compare`    | 共享对照   | 和别人发布的理解对照，发现不同的路径或分歧 | conflict、source    |
|      | `review`     | 间隔复习   | 按状态衰减安排回顾                         | confidence          |

默认工作流：

| 工作流          | 步骤                                                    | 编排方式      | 引导强度 |
| --------------- | ------------------------------------------------------- | ------------- | -------- |
| `speedrun` 速通 | goal → diagnose → map → explain → recall → distill      | 固定          | 给提示   |
| `deep` 长期积累 | 全部 16 个模块                                          | agent 决定    | 只提问   |
| `practice` 应用 | goal → diagnose → explain → example → practice → feynman → distill | 固定 | 给提示   |

## 4. 系统结构

```text
宿主 agent（Claude Code / Codex / WorkBuddy …）
  │  MindLink skill：告诉 agent 何时调用哪些工具
  │  MCP（每个用户一个令牌）
  ▼
MindLink 启动器 = Episteme service + MindLink 场景配置（profile）
  ├─ Episteme 工具：recall · propose · reflect · distill · thread_*（ADR 0015）
  ├─ MindLink 工具：project_open · workflow_next · workflow_report · guide_questions
  ├─ REST /api/v1：理解、建议审阅、发布 / 复用、线程、场景记录
  └─ Workspace（web 入口）：项目、线程树、审阅队列、进度、复习安排、浏览与复用、托管开关
          │
          ▼
     一份图谱（JSONL），按 actor 和可见性隔离；所有人共享一个服务
```

## 5. 时间线

依赖关系决定了顺序：Episteme 的身份 → 可见性 → 发布，这条线是关键路径。所有不依赖它的工作（模块内容、竞品分析、宿主 skill、MindLink 引擎），第一周就同时开始。

| 波次 | 日期        | Episteme                                                                    | MindLink                                                              | 其他               |
| ---- | ----------- | --------------------------------------------------------------------------- | --------------------------------------------------------------------- | ------------------ |
| W0   | 10/17–10/20 | 合并清理 PR（M0）；ADR 0012–0016 定稿                                       | 改名                                                                  | 真实宿主跑通（V1） |
| W1   | 10/20–10/27 | 只提供已注册的等级（M2）；场景配置与扩展点（M3）；身份与令牌（S1）          | 固定 Episteme 版本（M1）；模块格式与加载器；16 个模块内容             | discussion 仓库骨架 |

| W3   | 11/03–11/10 | 发布 / 浏览 / 复用 / 更新 API（S5–S7）；托管确认（0016）；分层上下文        | 共享视图；引导式提问；线程与进度视图；宿主 skill                      | —                  |

**进度落后时按这个顺序砍：** 先顺延 Episteme 对外发布（X1），再砍更新通知（S7），再砍用户自定义模块的分享，再砍分层上下文（改用现有检索），最后砍 `practice` 工作流。共享、默认工作流、引导式提问这三个核心点不砍。

## 6. 协作规则（给所有同学和他们的 AI）

- 每个 issue 一个分支，从最新的 `origin/main` 切出，分支命名为 `<type>/<short-topic>`；提交 draft PR，正文写 `Closes #编号`。不要直接推 `main`，不要把一个分支叠在另一个未合并的分支上。完整规则见 [`AGENTS.md`](../../AGENTS.md)。
- 跨仓库的改动，先合并 Episteme，再在 MindLink 里改 `episteme.ref`（ADR 0013）。
- **Windows 用户：** 克隆时加上 `-c core.autocrlf=false`。否则提交钩子里的格式检查会因为 CRLF 换行，把每个文件都报成格式不对。
- issue 里的提示词可以直接交给 AI。AI 遇到和 issue 冲突、或者不确定的地方，应当停下来在 issue 里提问，不要自己猜。
